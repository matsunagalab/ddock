## 実装した4機能

| 機能 | 主なファイル | 実装と境界 |
| --- | --- | --- |
| 型別物理場と微分FFT | `src/zdock/inducedfit/typed_potential.py`, `typed_fft.py` | ff14SBの電荷・σ・ε、C2 coreのLJとscreened Coulomb。既定mass補間。coarse FFTは候補生成だけに使い、実energyは連続pair potentialで再評価 |
| 物理strainと応答K | `physical_prior.py` | apo-onlyにff14SB/OBC2/ACE＋全原子Cartesian anchorを最小化し、定常基準から真のtorsion force/HVPでKを構築。負strainや固有値をclipしない |
| 原子別変位制約 | `atom_constraints.py` | CA振幅ballと各原子の線形変位ballの凸問題。SciPy SLSQP＋独立KKT certificate。有限変位と実energyの検証は必須 |
| 接触力から新方向を追加 | `adaptive_contact.py` | 予測接触8 Å内のtorsion mask、既存4 ANM方向とのH直交、最大4追加方向。HVP/PCGで解く。独立random対照も実装 |

統合は `physics_pipeline.py` と `scripts/run_physics_induced_fit_pair.py`。
旧runnerを置換しておらず、新しい実験用CLIに分離している。5armは
`rigid ball8 atom8 contact8 random8`。共通apo・回転・格子を使い、contact/randomは
新しい基底で2回目のFFTを実行する。同じ最終8modeでも同じwall timeではない。

cross-partner screened pair energy＋monomer OBC2 strainは明示したhybrid modelであり、
全Amber complex energyや結合自由エネルギーではない。anchorは10 kJ/mol/Å²/atom。
現kinematicsはopen-chain backbone φ/ψで、抗体χ、disulfide、有限loop closureは未対応。

数値前処理は物理を変更しない。adaptive PCGは入力apoの `G=10 JᵀJ+I` をlocal maskに制限し、
H直交制約内で逆作用を使う。random分布は変更しない。精密化では振幅blockを
`-solve(K,g)` で前処理する。再帰残差≤1e-5、再計算した物理残差≤5e-5、曲率・実変位・
energy gateを維持する。`--adaptive-preconditioner none --refinement-preconditioner fixed`
は初回smokeの数値方式で、元sourceはsmoke_v1の`source_snapshot/`にも残っている。

## 実測結果と、まだ解けていない問題

実apoは1A2P B / 1A19 A、既に繰り返し使ったdevelopmentの1組でありheld-out testではない。
128 rotations、4 peaks/rotation、pool50、Top5、8 refinement steps/64 evaluations、seed0。
全5arm×5候補をexportし、推論完了後に別プロセスで公式DockQを評価した。

- 新方式の最良DockQは **0.049557**。旧pilot R1 best5の **0.201863** を上回っていない。
  ただし旧方式とは準備・score・prior・探索/精密化条件が変わっており、単一改良の比較ではない。
- 全5armでpool50の集合、選択Top5の集合・順序、最終energy順位が同じだった。
  raw response512件は固定8modeに対しcontactで2件、randomで1件が変わったが、いずれもpool外。
- 評価専用pool oracle bestは **0.187854**、選択Top5の変形前bestは **0.035106**。
  poolにも選択Top5にもDockQ≥0.23は0件。候補保持と選択の両方に課題がある。
  oracleを予測順位として使わず、今後の推論にnativeを混ぜない。
- 固定8modeのK traceの **75.6%** はanchor由来。これはKの分解診断であり、
  binding energyに占める割合ではない。priorの強さと数値最適化の制限を分けて調べる必要がある。
- 柔軟4armの検証200/200候補はscale=1で採用。fallback、shrink、活性制約は全て0。
  ball8の最大提案CA normは0.00189554 Å、保守ball半径0.0781264 Åの2.426%。
  `-K⁻¹g`との差は最大1.96e-18 Å。ball8/atom8は50提案・検証振幅がbitwise一致し、
  最終5候補の両分子全座標もbitwise一致した。このpilotでは原子別制約の利点を評価できていない。
- 全25精密化が64評価上限で終了し、受理stepは6〜7。最終内部CA RMSD最大は
  ball/atom0.000145557 Å、contact0.000236959 Å、random0.000172320 Å。
  小変形の原因をanchorだけと断定せず、共有line searchと評価予算も診断する。

wall timeは **2387.262秒（39.8分）**、peak RSS **6.737 GB**。
共有準備/初回FFT520.546秒、arm別にrigid206.436、ball189.419、atom191.451、
contact649.918、random626.528秒。cache予算4 GBは保持spectrumの予算で、process RSS上限ではない。

## Linux/NVIDIAへの次の実装

まず環境・精度・実装変更を分離する。順序は **Linux CPU fixture → CUDA probe →
小系energy/gradient/JVP/HVP比較 → 4rotation smoke → 128rotation**。
現在はGPU実装そのものが必要であり、CLIに存在しない`--device cuda`を渡しても動かない。

1. `typed_potential.py`、`typed_fft.py`のCPU/float64検査とCPU tensor生成をdevice対応にする。
   `physics_pipeline.py`のFFT cache/rotation loopもGPUに常駐させる。初期比較はfloat64を維持する。
2. `adaptive_contact.py`、`atom_constraints.py`、`physical_prior.py`もCPU float64を明示要求している。
   GPU FFTとCPUの小さなSciPy制約solverを組み合わせる段階移行は可能。
   どのtensorをいつ転送するかをAPIで明示し、CPU前提を単に削除しない。
3. `physical_prior.py`と`atomistic_score.py`はOpenMM **Reference固定**。
   coordinates/forcesのNumPy・CPU往復もある。CUDA Platformを明示選択できるbackendを追加し、
   まず`Precision=double`、必要な`DeviceIndex`、再現性用`DeterministicForces=true`で検証する。
   GPUが列挙されるだけでなく、小さな実Contextでenergy/force計算が通ることを確認する。
4. 回転ごとのFFTをmemory budget内でbatch化し、`float(tensor)`、`.item()`、bool判定、
   CPUへのコピー、頻繁な進捗保存による同期を計測・削減する。保持cacheだけでなくworkspace、
   batch中間体、peak VRAMも記録する。CPUと同じquaternion列・pose key・順位規則を保持する。
5. 保存した同一座標・θ0・方向をCPU/CUDAへ渡す。HVPはforce差分なので、
   `h=1e-4`と`h/2`、対称性、K固有値、真のCG残差、
   非線形energy差をdoubleで比較する。mixed/single化はその後の独立ablation。
   KKT/定常性/変位gateを速度のために緩和しない。GPUのFP64性能と転送費用は実機測定する。

簡単な環境probe例。これは全モデルのGPU対応・精度を確認するテストではない。

```bash
nvidia-smi
.venv/bin/python - <<'PY'
import torch, openmm
print('torch', torch.__version__, 'cuda build', torch.version.cuda)
print('cuda available', torch.cuda.is_available())
print('OpenMM', openmm.__version__)
print('platforms', [openmm.Platform.getPlatform(i).getName() for i in range(openmm.Platform.getNumPlatforms())])
if torch.cuda.is_available():
    print('GPU', torch.cuda.get_device_name(0))
    x = torch.ones((8, 8, 8), device='cuda', dtype=torch.float64)
    y = torch.fft.rfftn(x)
    torch.cuda.synchronize()
    print('float64 FFT finite', bool(torch.isfinite(y).all()))
PY
```

OpenMMのCUDA propertiesとdouble精度については
[公式Platform-specific properties](https://docs.openmm.org/latest/userguide/library/04_platform_specifics.html)
を参照。PyTorchの[公式rfftn仕様](https://docs.pytorch.org/docs/2.15/generated/torch.fft.rfftn.html)では、
CUDA halfは変換する各軸長が2冪に制限される。今回のgrid79、zero-padding後157のまま
halfへ置換する計画にはしない。この参照は2.15 docsであり、lock内Linux2.6.0の実動作は別途確認する。

高速化と予測精度は別の問題。backend比較中は物理・seed・候補予算を固定する。
精度側の次の診断は、coarse格子/角度coverage、poolの選択score、anchor由来の剛性、
rigid/flexible blockのline searchと64評価budgetを分ける。変更条件は事前に記録し、
1組の既知DockQに合わせた調整をheld-out改善と呼ばない。
